# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ClubTouch3 is a German-language web POS ("Kassensystem") for a club bar: touch sales screen, member accounts with balances, stock, purchase documents, invoices, PDF/CSV reports, a live "Clubscore" highscore, and a digital-signage slide editor. UI strings, comments, commit messages and error messages are in German; keep new user-facing text in German.

Monorepo with two independent npm projects (no root package.json, no workspaces):

- `apps/backend` – Express 5 + Prisma 6 + PostgreSQL 15 + Socket.io, plain CommonJS JS (no build step). Needs Node >= 22.12 because `archiver` 8 is an ES module loaded via `require` (`new ZipArchive(...)` in `receiptService`); `package.json` overrides `readdir-glob`'s `minimatch` to keep `npm audit` clean.
- `apps/frontend` – Create React App (react-scripts 5), React 19, MUI 7, TanStack Query 5, React Router 7.

## Commands

Run from the respective app directory. Install with `npm install` in each.

Backend (`apps/backend`):

```bash
npm run dev                    # nodemon src/server.js
npm start                      # node src/server.js
npm run prisma:generate        # regenerate client after schema changes
npm run prisma:migrate         # prisma migrate dev (creates a migration)
npm run prisma:migrate:deploy  # apply migrations (used in Docker CMD)
npm run prisma:seed            # idempotent: first admin (only if no user exists) + Clubraum article catalogue with images
npm run prisma:studio
```

Frontend (`apps/frontend`):

```bash
npm start                      # CRA dev server on :3000
npm run build                  # static build into build/
npm test                       # react-scripts test (jest, watch mode); CI runs it with --watchAll=false
npm test -- --watchAll=false src/components/layout/Layout.test.js   # single file
```

Backend has no test runner or linter; verify with a small fetch script against a local instance. CI (`.github/workflows/ci.yml`) runs `npm ci` in both apps, `node --check` over `src` and `prisma` plus `npx prisma validate` in the backend and `npm run build` in the frontend; plus the frontend jest tests (`Layout.test.js`; `package.json` maps `react-router` to its CommonJS build for jest 27 and `setupTests.js` polyfills `TextEncoder`). There are no backend behavioural tests in CI.

Migrations on the local test DB: `prisma migrate dev` fails there (no permission for the shadow database). Create migrations with `prisma migrate diff` (from the migrations folder to `schema.prisma`, `--script`), save the SQL as a new migration folder and apply it with `prisma migrate deploy`.

Docker (from `docker/`): `./manage.sh start|start-dev|stop|rebuild|logs-f|backup|restore|clean`, or `manage.ps1` on Windows (both call `docker compose`). `docker-compose.yml` brings up db + backend + frontend (+ adminer under `--profile dev`); build contexts are `../apps/...`, uploads live in the named volume `uploads`, the frontend container gets `BACKEND_URL=backend:3001` for nginx, and the backend runs migrate deploy + seed on every start. Verified with Docker 29 in production mode (`BACKEND_NODE_ENV=production` needs real secrets and `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`).

### Local dev port gotcha

The CRA dev server proxies `/api` to `http://localhost:3001` (`proxy` field in `apps/frontend/package.json`), but the backend defaults to `PORT=8080` when unset. Set `PORT=3001` in `apps/backend/.env` for local development. The frontend needs no `.env`: `REACT_APP_API_URL` defaults to `/api` and `REACT_APP_WS_URL` to `/`.

### Backend environment

There is no `apps/backend/.env.example`; `docker/.env.example` and `docker/docker-compose.yml` are the reference for variable names. Required (`server.js` exits at start without them): `DATABASE_URL`, `JWT_SECRET`, `JWT_REFRESH_SECRET`, `JWT_EXPIRE_TIME`, `JWT_REFRESH_EXPIRE_TIME`; with `NODE_ENV=production` both secrets must be at least 32 characters and no placeholder. `docker/docker-compose.yml` requires the secrets (`${VAR:?…}`); `docker/docker-compose.simple.yml` has fixed placeholder secrets and is for development only. Optional: `PORT`, `NODE_ENV`, `BCRYPT_ROUNDS`, `PUBLIC_BALANCE_PIN` (shared PIN for `/check-balance`, default `666`), `FRONTEND_URL` (socket CORS in production, exact match, comma-separated list allowed), `PUBLIC_BASE_URL` (upload URLs), `EXPORT_DIR` (defaults to `/tmp/exports`), `INVOICE_SENDER_NAME` / `INVOICE_PAYEE_NAME` / `INVOICE_IBAN` / `INVOICE_BIC` / `INVOICE_REF_PREFIX` (defaults are the real Clubraum sender and KJG bank account in `invoiceService.DEFAULT_CONFIG`; BIC and e-mail are optional and omitted when empty; the invoice PDF shows no VAT lines and uses `src/assets/logo.png`).

## Architecture

### Backend request flow

`src/server.js` → `src/app.js` (Express app, mounts all routers under `/api/*`, serves `./uploads` statically) → `src/routes/*.js` → `src/controllers/*.js` → `src/services/*.js` → `src/utils/prisma.js` (singleton PrismaClient).

- Routers apply `authenticate` (Bearer JWT, loads the user and checks `active`, sets `req.user`) and `authorize('ADMIN', 'CASHIER', ...)` from `src/middleware/auth.js`. Roles are `ADMIN | CASHIER | ACCOUNTANT`; the user-facing role table is in `README.md` and the frontend mirror of the `authorize()` rules is `apps/frontend/src/config/permissions.js` (`can('sell')` etc. from `useAuth()`, used only to hide menu items, routes via `ProtectedRoute roles={PERMISSIONS.x}` and buttons). Change both when a rule changes. Notable rules: ACCOUNTANT cannot sell or edit articles/customers/purchases/invoices (read only) but may delete purchase documents, close fiscal years and cancel cash movements; CASHIER cannot create/close fiscal years or delete purchase documents/invoices; ads and the screen assignment are ADMIN + CASHIER; `GET /api/exports` only lists the reports the role may download. `routes/public.js` (`/api/public/*`) is deliberately unauthenticated for kiosk screens: highscore, ads, screen assignment, and balance lookup (`POST /public/customer/balance` with name + shared PIN `PUBLIC_BALANCE_PIN`; wrong PIN = 403, not 401, so the axios refresh interceptor stays out of it; wrong PIN or unknown name count towards an in-memory limit of 10 per IP per 15 min). `app.js` sets `trust proxy` to private ranges only, so `req.ip` is the real client behind nginx/Railway and the login/PIN throttles are per client, not global.
- Input validation is `express-validator` chains in `src/middleware/validation.js` followed by `handleValidationErrors`. Optional string fields that the frontend sends as `""` must use `.optional({ values: 'falsy' })`, otherwise the empty string fails the length check.
- Users and login (`userService`, `authController`): login accepts e-mail or username, both compared case-insensitively (`mode: 'insensitive'`); e-mails are stored lower-case, usernames as typed but unique ignoring case, empty username is stored as `null`. Tokens carry a random `jti` because two logins of one user in the same second would otherwise produce identical tokens (`Session.token` is unique). Login has an in-memory throttle (10 failures per identifier+IP per 15 min → 429). `POST /auth/change-password` (own password, current password required, other sessions of the user are deleted); admins set other users' passwords via `PUT /users/:id`, whose response carries `passwordChanged`. Deactivating a user deletes their sessions. `DELETE /users/:id` always only deactivates (never removes the row). E-mails are not run through `normalizeEmail`. `POST /auth/refresh` rotates the refresh token but tolerates parallel calls: the old token still yields the new tokens for 30 s (`ROTATION_GRACE_MS`), so concurrent refreshes of several tabs do not log the user out. `POST /auth/logout` works without `authenticate`. Socket.io CORS in production compares exactly against `FRONTEND_URL`.
- Controllers are classes exported as singleton instances; they catch errors and send German messages. Business logic that mutates money or stock lives in services and runs inside `prisma.$transaction`. Controllers write `AuditLog` rows after mutating calls.
- `app.js` installs a JSON replacer that converts BigInt to numbers. Prisma `Decimal` has its own `toJSON()` and therefore reaches the client as a STRING (`"2.50"`); the frontend must convert (`Number(...)`), the article hook normalizes `price`/`stock`. Raw SQL results (`$queryRaw`) still need `Number()` on the server side when used in arithmetic.
- Request limits and errors (`app.js`): JSON/urlencoded body limit 1 MB (exception `/api/ads` with 50 MB for slide snapshots); a central error handler maps Multer errors to 400 and never sends a stack trace. Business errors are thrown as `userError(message, status)` (`src/utils/httpError.js`) and answered by `sendError` with 4xx and `{ error: "<German message>" }`; anything else is a generic 500 and the Prisma text only goes to the log.
- Realtime: `src/utils/websocket.js` wraps Socket.io. Every socket joins the `highscore` room; the auth token is optional (anonymous connections allowed). `transactionService.createSale` emits `sale:new` and triggers `highscoreService.updateAfterSale`, which emits `highscore:update` (the full Clubscore object, see below; `highscore:display` carries the display setting).

### Domain rules encoded in services

- Sales (`transactionService`): `Transaction.type` is `SALE | REFUND | EXPIRED | OWNER_USE`, but `POST /transactions` accepts only `SALE | OWNER_USE | EXPIRED` (`REFUND` only arises from cancelling); the old `quick-sale` endpoint is gone. Only `SALE` has a non-zero `totalAmount`; `EXPIRED` and `OWNER_USE` ("Auf den Wirt") book stock movements with amount 0. Stock may go negative (warning + `NEGATIVE_STOCK_WARNING` audit, never a block). Paying by `ACCOUNT` enforces a hardcoded 10 EUR overdraft limit. Cancelling (`POST /transactions/:id/cancel`) works for `SALE`, `OWNER_USE` and `EXPIRED` and creates a linked `REFUND` transaction rather than deleting; for the money-less types the refund is 0 EUR and only stock goes back. Cancelling is atomic (status check, refund row, stock and balance in one transaction) and works once per transaction. Idempotency for the offline queue: sale and top-up requests may carry `clientId` (8–64 chars, unique, a repeat returns the already booked row) and `clientCreatedAt` (used as booking time if valid, not in the future and at most 7 days old; `src/utils/clientRequest.js`, migration `20261110140000_sale_client_id`).
- Raw SQL against `DateTime` columns (`timestamp(3)`, naive UTC): always compare as `"createdAt" >= (${date}::timestamptz AT TIME ZONE 'UTC')`. Without the cast Postgres converts the column in the session time zone, which shifts every window by the local UTC offset on a non-UTC database (the local dev cluster is Europe/Berlin, Railway is UTC). Prisma ORM queries are unaffected.
- The "business day" starts at 06:00, not midnight (the bar night runs past midnight). `BUSINESS_DAY_START_HOUR` and `businessDayWindow()` in `src/utils/businessDay.js` are the single source for every daily window: daily summary, dashboard/transactions KPIs, exports and the Clubscore. Never call `new Date('YYYY-MM-DD')` on a query param (that is UTC midnight = 02:00 local); use `parseLocalDate` / `endOfLocalDay` from the same module. A date-only string means "that business day", a timestamp before 06:00 belongs to the previous one. The backend sets `process.env.TZ ||= 'Europe/Berlin'` at the top of `server.js` (and `ENV TZ` in the Dockerfile) because Railway runs in UTC and the 06:00 day start and the 1 January are local times.
- Clubscore (`highscoreService`): daily and yearly rankings are computed live from non-cancelled `SALE` transactions of articles with `countsForHighscore` (switch "Zählt für den Clubscore" in the article dialog; raw SQL, top 20, revenue or quantity mode, RANK semantics with tie-breaker "reached first", `gapToPrev` = distance to the next better rank). The day is the 06:00 business day; the year is the calendar year from 1 January or from the latest `RESET_YEARLY_HIGHSCORE` `AuditLog` row of that year (reset = ADMIN "Jahr zurücksetzen", archives rankings and teams in `changes`). A finished calendar year without reset is archived automatically as `ARCHIVE_YEARLY_HIGHSCORE` (never `RESET_…`, that one is the start marker); `getArchive()` reads both (`auto` flag). `getAllBoards()` builds one object `{daily, yearly, teams, goals, events, stats, period, serverTime}` with a 5 s cache; the same object is served by `GET /api/public/highscore/all` and pushed as `highscore:update`. `refreshBoards()` is called after sale, cancel, reset, goal changes, customer changes (name, nickname, group, active), group changes and article `countsForHighscore`/`active` changes; `init()` in `server.js` schedules a timer to the next 06:00 business-day start. Events (`GOAL_REACHED`, `NEW_LEADER_DAY/YEAR`, `TEAM_LEAD_DAY` = big overlay; `OVERTAKE`, `NEW_TOP20` = ticker) are detected by comparing with the previous state after a sale only (ring buffer of 20, cleared at 06:00, none after start/reset); `GOAL_REACHED` is also an `AuditLog` row (`HighscoreGoal`, feeds `goals.monthReached`) and names the buyer (`reachedBy`). Goals (max 6; kinds `ARTICLE | CATEGORY | REVENUE`, optional `groupId` = team goal, `movingTargets` raises the level) live in `SystemSetting` `clubscore.goals` (legacy fallback: `AuditLog` `HighscoreGoals`), templates in `clubscore.goalTemplates`; the frontend must send each goal's `id` back or its level/`reachedAt` restart. Validation chains are in `middleware/highscoreValidation.js`. Indexes `Transaction(customerId, createdAt)` and `TransactionItem(articleId)` exist for these queries. Invoice settings also live in the `SystemSetting` key-value table.
- Groups / teams (`CustomerGroup`, `/api/customer-groups`, KjG groups like "Panther"): a customer is in zero or one group (`Customer.groupId`, `onDelete: SetNull`); a group has `color`, optional `emoji` and uploaded `imageUrl` (`uploads/groups/`, 256 px WebP via `fileUploadService.processGroupImage`). `isGroupAccount` marks a shared account many members book on: it ranks like a customer in the individual boards and counts to the team total, but not as a head. Team boards: `total` = all group sales incl. the group account, `heads` = members with a counting purchase in the period (group accounts excluded), `perHead` = total / heads (`–` and no `perHeadRank` with 0 heads). GET for all roles, POST/PUT ADMIN+CASHIER, DELETE ADMIN. `CUSTOMER_BASIC_SELECT` includes `group`. Frontend: `components/customers/GroupBadge.js` (image → emoji → coloured initial) and `GroupManagerDialog.js` (button "Gruppen" on `/customers`).
- Clubscore display setting (`SystemSetting` `clubscore.display`: `view amount|count|teams|rotate`, `rotateViews`, `rotateSeconds`, `board both|day|year`, `ticker`) is global for all screens: `GET /api/public/highscore/display`, `PUT /api/highscore/display` (ADMIN, CASHIER) → socket `highscore:display`. `/public/highscore` takes URL params `view`, `board`, `ticker=0|1` first and falls back to the stored setting live.
- Purchasing: `PurchaseDocument` is either `RECHNUNG` (supplier invoice, money) or `LIEFERSCHEIN` (delivery note, goods); delivery notes can be attached to one invoice via `rechnungId`. Items store the final base unit plus how they were entered (purchase unit × quantity), driven by `Article.purchaseUnit` / `unitsPerPurchase`. Both document types book stock for their own items; linking/unlinking (`rechnungId`) is documentary and never moves stock, so an invoice with attached delivery notes normally carries no items of its own (`components/purchases/LinkedLieferscheineInfo.js` explains this in the UI and warns about extra items; deliberately no backend block because extra articles are legitimate). `PurchaseDocument.enteredBy` is a free-text name ("Eingetragen von"; the on-site tablet uses a shared account, so it is not the user) prefilled with the account name on create and always editable; `components/purchases/EnteredByField.js` offers the names from `GET /purchase-documents/entered-by` (most frequent first). `GET /purchase-documents` filters by `startDate`, `endDate`, `supplier` (exact), `paid`, `search`; list rows include `lieferscheine[].items`, `GET /:id` includes `rechnung`.
- Auslage (a member paid a supplier invoice privately): a `RECHNUNG` paid with `paymentMethod = ACCOUNT` requires `reimbursedCustomerId` ("Ausgelegt – dem Kundenkonto gutschreiben", whole amount only). `purchaseDocumentService` then books an `AccountTopUp` with `method = REIMBURSEMENT` and `purchaseDocumentId`, crediting the customer. Setting the document unpaid or deleting it books a negative counter top-up "Storno Auslage …"; while the credit exists, amount, method and customer are locked (400 with `userError`), and `customerService.reverseTopUp` refuses REIMBURSEMENT rows. REIMBURSEMENT is never cash, bank or top-up income (every aggregate filters `method: CASH|TRANSFER`); the EÜR expense stays the paid RECHNUNG. Legacy documents paid `ACCOUNT` without a customer have no credit and stay editable. Frontend: `components/purchases/ReimbursementCustomerField.js` (picker + `PAYMENT_METHOD_LABELS`) and `MarkPaidDialog.js` (mark-paid from the list).
- Customer contact data (`Customer.company/street/zip/city/phone/email`, all optional) is visible and editable for all three roles (`CONTACT_ROLES` in `customerController`; `stripContact` and the input filter stay in place for any future role); relations that reach the socket (`transactionService`, `invoiceService`) use `CUSTOMER_BASIC_SELECT` from `src/utils/customerSelect.js` instead of `customer: true`; `/api/public` never returns it. In `Invoices.js` picking a customer prefills real name and address and sends `customerId`; the checkbox "Anschrift beim Kunden speichern" parses the address (last line `PLZ Ort`, above it street, then company) and PUTs it to the customer.
- Customer account statement (`customerService`, statement PDF/CSV): only `ACCOUNT` transactions and top-ups change the balance (cash/card sales do not); the statement returns `openingBalance` and `closingBalance` derived backwards from the current balance, and `openingBalance + topUps − spent = closingBalance`. `updateCustomer` no longer touches `lastActivity` (only sales/top-ups count as a visit at the bar). Customer names are unique ignoring case.
- Accounting (`accountingService.getProfitLoss`) is the single source for EÜR numbers (UI, EÜR PDF, year-end): income = `SALE` transactions (cash + account) + paid `Invoice` (`paidAt` in range); expenses = paid `RECHNUNG` documents by payment date (`paidAt`, fallback `documentDate` for old documents without one; cash principle, not the document date). `OWNER_USE`/`EXPIRED` are never income; they are reported as `nonRevenue` (quantity + value at sale price). Top-ups are `liquidity.topUps` (cash inflow but a liability), plus `liquidity.guestBalanceEnd`, `liabilities.unpaidPurchaseDocuments`, `receivables.unpaidInvoices`. Legacy fields (`summary.*`, `details.*`) stay for the frontend.
- Customer invoices (`invoiceService`): stock is booked out exactly while the status is not `CANCELLED` (creating books out, cancelling via `PATCH …/status` or `DELETE` books it back exactly once, a cancelled invoice stays cancelled). Status values `DRAFT | SENT | PAID | CANCELLED` with a transition check; hard delete (`DELETE ?hard=…`) only for `DRAFT` and `CANCELLED`. Updates take only a whitelist of header fields. Numbers come from `src/utils/numberSequence.js` (counter in `SystemSetting`, e.g. `invoice.lastNumber.<year>`, a number is never reused even after deleting the last document; callers retry on P2002). Purchase document numbers use the same module.
- Customer invoices (`Invoice`): `paymentMethod` (`CASH | TRANSFER`, nullable) is set when an invoice is marked `PAID` (`PATCH /invoices/:id/status` requires it, optional `paidAt` not in the future; any other status clears both). Invoices paid before 09/2026 have no payment method and count as bank. EÜR income counts every paid invoice regardless of payment method.
- Purchase documents: `paidAt` ("Bezahlt am", `components/purchases/PaidAtField.js`) is enterable when marking paid and is the date Kasse/Bank/EÜR use; amounts may be entered with a decimal comma; linking checks (delivery note ↔ invoice) are validated server-side.
- Cash counts (`CashCount`, `cashCountService`, `/api/cash-counts`): the till is not counted daily; a count can be made at any time. Expected = previous `countedTotal` + cash `SALE` + cash `REFUND` (negative) + cash `AccountTopUp` + cash-paid customer invoices (`cashInvoices`, by `paidAt`) − cash-paid `RECHNUNG` (by `paidAt`, fallback `documentDate`) since the previous count; without a previous count the baseline is 0. `countedTotal` is computed server-side from `denominations`; the derivation is frozen in `breakdownJson`. Cancelled sales are deliberately included (the refund row books the cash going back out). Cash movements count by `max(occurredAt, createdAt)` (a movement booked after the last count never falls before it), and a cash-paid `RECHNUNG` or customer invoice whose `paidAt` lies before the latest count is rejected with 400 (it would silently change a counted period).
- Cash movements (`CashMovement`, `cashMovementService`, `/api/cash-movements`): till movements without a sale. Types `DEPOSIT_TO_BANK` / `OTHER_EXPENSE` reduce the till, `WITHDRAWAL_FROM_BANK` / `OTHER_INCOME` increase it; `amount` is always positive, cancelling sets `cancelled` instead of deleting. They feed the cash-count expected value (`cashCountService.getCashMovements` → `bankDeposits`, `bankWithdrawals`, `otherIncome`, `otherExpense`, frozen in `breakdownJson`). For the EÜR only `OTHER_INCOME` (income) and `OTHER_EXPENSE` (expense) count; bank deposits/withdrawals are liquidity only (`liquidity.cashMovements`). A note is mandatory for the `OTHER_*` types.
- Receipt review for the auditor (`receiptService`): `GET /api/accounting/fiscal-years/:id/receipts` and `GET /api/purchase-documents/receipts?startDate&endDate` list every `PurchaseDocument` (RECHNUNG and LIEFERSCHEIN) of the period with `hasNachweis` / `nachweisMime` and `enteredBy` (shown in `ReceiptReview`, the CSV column "Eingetragen von" and under the supplier in `Belegliste.pdf`); the `.zip` variants stream all upload files (named `<documentNumber>_<supplier>_<amount>.<ext>` via `archiver`) plus `Belegliste.csv` and `Belegliste.pdf`. Deliberately no tick-off/approval flag.
- Bank reconciliation (`accountingService.getBankReconciliation(start, end, { endAt })`, `GET /api/accounting/bank-reconciliation?startDate&endDate` and `/fiscal-years/:id/bank-reconciliation`): expected bank balance = opening + movements since the opening. Opening = the latest `BankBalance` with `isOpening` (Anfangsstand, `openingSource` `ANFANGSSTAND`, movements counted from its `date`) if newer than the latest closed `FiscalYear` ending before the period; else that year's bank accounts (`VORJAHRESABSCHLUSS`, movements from the day after its `endDate`); else 0 (`KEIN_VORJAHR`, from the requested start). The window always starts at the opening, never later, so nothing between opening and requested start is lost. Card payments (`CARD` sales + `CARD` top-ups) are grouped per day as `CARD` movements, minus an estimated fee (`SystemSetting` `card.feePercent`, `outflows.cardFees`); in the EÜR card sales count in full (`incomeByType.card`) and `details.cardFeesHint` only reminds to book the real SumUp statement as a receipt. Statement checks: `BankBalance` without `isOpening` (`/api/accounting/bank-balances`, GET all roles, POST/DELETE ADMIN+ACCOUNTANT); `listBankBalances` compares each with the expected value at its exact time (one reconciliation per calendar year). Further: + `DEPOSIT_TO_BANK` + `AccountTopUp.method = TRANSFER` + paid `Invoice` with `paymentMethod` `TRANSFER` or `null` (`paidAt`; cash-paid ones are reported as `invoicesPaidCash` and belong to the till) − `RECHNUNG` with `paymentMethod = TRANSFER` (`paidAt`, fallback `documentDate`) − `WITHDRAWAL_FROM_BANK`. There is no bank ledger: fees, membership dues and donations are outside the app, so a difference is expected and only has to be explainable. The snapshot (`detailsJson.bankReconciliation`, version 3) freezes it with `actual` (sum of entered `bankAccounts`) and `difference`; the closed-year endpoint returns `frozen: true` from the snapshot and the year-end PDF section "Bank-Abstimmung" renders from it.
- Closing a `FiscalYear` requires a cash count within `[startDate, endDate + 1 day]` (400 otherwise; `cashCountId` may be passed explicitly). `cashOnHand` comes from that count, never from the request body. Fiscal years must not overlap (400). The full snapshot (`version: 4`) lives in `YearEndReport.detailsJson`; version 4 adds `cashCounts`, `corrections`, guest balances at the cut-off date with a balance reconciliation and the cash/bank-to-money-stock bridge (`services/yearEndExtrasService.js`), rendered as additional year-end PDF sections; inventory value counts negative stock as 0; the year-end PDF renders only from it once the year is closed, and as a live "ENTWURF" while it is open.
- Soft lock for closed fiscal years (`src/utils/closedPeriod.js`): a write whose relevant date (before OR after the change) lies in a closed `FiscalYear` (start 00:00 to end 23:59:59 local, closed years cached 10 s, `closeFiscalYear` invalidates) answers **409** `{ error, code: 'CLOSED_PERIOD', fiscalYear }` and changes nothing, unless the request carries the header `X-Confirm-Closed-Period: 1`; then it runs and writes, in the same DB transaction, one `AuditLog` `CLOSED_PERIOD_CHANGE` per affected year (`changes: { fiscalYearId, fiscalYearName, operation, description, amountBefore, amountAfter, kind, effect }`, `effect` = impact on the year's surplus, `null` = neutral). Services call `closedPeriod.guard(dates, confirmClosed, tx)` + `logChange(tx, years, …)`; controllers pass `{ confirmClosed: closedPeriod.isConfirmed(req) }` and answer via `sendClosedPeriod` (shared `utils/httpError.sendError` forwards `error.payload`). Covered: purchase documents create/update/delete (document date + payment date; pure pay/unpay only looks at the payment date, so paying last year's invoice in the new year is not locked; saving without real change never asks), invoices status/edit/cancel/hard delete (`paidAt` old/new, `createdAt` for edit/cancel/delete), cash movements create (`occurredAt`) and cancel, sale cancel and top-up cancel (original `createdAt`), `BankBalance` add/delete. Not locked: link/unlink of delivery notes, cash counts (always now), new sales. Offline sales/top-ups whose `clientCreatedAt` lands in a closed year are accepted and logged automatically as operation "Offline-Nachbuchung". `GET /accounting/fiscal-years` returns `closedPeriodChanges` per closed year (warning chip in `pages/ProfitLoss.js`); the closed year's PDF gets a live cover note and an annex after the signatures "Nachträgliche Änderungen nach dem Abschluss" (snapshot `summary` vs live `getProfitLoss`, split into logged effect and unexplained difference, plus the log list). Frontend: the response interceptor in `services/api.js` catches 409 + `CLOSED_PERIOD`, asks via `components/common/ClosedPeriodDialog.js` (mounted once in `App.js`, reached through `services/closedPeriodPrompt.js`) and repeats the same request with the header (FormData included); cancel rejects with the original error, so pages need no changes.
- All money and quantities are `Decimal(10,2)` in Prisma; services generally cast to `Number` for arithmetic.

### Uploads and exports

All uploads live under `UPLOADS_DIR` from `src/utils/uploadsDir.js` (env `UPLOADS_DIR`, else Railway's `RAILWAY_VOLUME_MOUNT_PATH`, else `<cwd>/uploads`); never build upload paths from `process.cwd()`, use `toPublicUrl(absPath)` / `fromPublicUrl(url)` from that module. `fileUploadService` writes `articles/{original,thumbnail,small,medium,large}` as WebP via sharp and `nachweise/` for receipt scans; `middleware/upload.js` stores ad slide media in `ads/` with a 500 MB limit. Stored URLs are relative (`/uploads/...`) so they work behind the nginx proxy. On Railway the directory is only persistent with a volume mounted on the backend service (declared as `backend-volume` in `.railway/railway.ts`); without it every deploy wipes article images, receipts and ads. Uploads live on the container filesystem: docker-compose bind-mounts `./apps/backend/uploads`, on Railway the volume `backend-volume` is mounted at `/app/uploads`.

Ads / digital signage: `AdSlide` rows are either an uploaded file (`imageUrl` under `/uploads/ads/`, image or video) or a designed slide (`slideData` JSON rendered live by `components/ads/SlideRenderer.js` on a fixed 1920×1080 canvas; `imageUrl` then holds a PNG snapshot). Admin routes `/api/ads` are ADMIN and CASHIER; multer errors map to 400, and deleting or replacing a slide removes its upload when nothing else references it. The public display `/public/ads` polls `GET /api/public/ads` every 60 s and restarts the rotation only when the fingerprint changed; the slide "Menü" element reads `GET /api/public/articles?category=` (active articles, name/price only) so it works without login. Menu element options (`components/admin/MenuOptions.js`, rows built by `buildMenuRows` in `components/ads/SlideElement.js`): `hidden` (article ids left out), `groups` (`[{id, label, articleIds}]`, one row per group at the position of its first article, "ab …" when prices differ, varieties listed small below; "Vorschlag" proposes groups of three or more articles with the same first word and price, `suggestGroups` in `MenuOptions.js`), `columns` 1|2 and `priceColor`. The menu never overflows: if the rows do not fit the element height the row size (`--rs`, base `fontSize * 0.4`) shrinks until they fit, down to 40 % / 16 px, measured unscaled so editor and screen match. Slide templates are in `components/admin/slideTemplates.js` (7 templates, black background, `slide()` assigns `zIndex` by list order; never derive z-order from a global counter, the template dialog builds every preview on each render). Fonts are bundled via `@fontsource` in `src/fonts.js` (Inter, Bebas Neue, Oswald, Permanent Marker, Monoton; imported in `index.js`), so slides look the same on every screen; `fontStack()` adds fallbacks for the older system fonts. PDFs are built with PDFKit in `exportService` (theme in `getTheme()`, brand name "Clubraum").

### Deployment

Railway deploys backend and frontend from the per-app Dockerfiles on every push to `main`. The infrastructure is described in `.railway/railway.ts` (IaC, replaces the old `railway.toml`; variables are unmanaged and live only in the dashboard; `npm install` in `.railway/`, then `railway config plan` before any `railway config apply`; the Postgres image is pinned there on purpose, the `postgres()` shorthand would switch the major version). The backend container runs `prisma migrate deploy`, then the idempotent seed, then `node src/server.js`; on a database without users the start fails on purpose until `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` are set (production has no default password). The frontend container builds the CRA app and serves it with nginx; `nginx.conf` is an envsubst template that proxies `/api`, `/uploads` and `/socket.io` to `$BACKEND_URL`, so the SPA only talks to same-origin paths.
